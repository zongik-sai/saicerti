## 만들 것

- 파일: `src/content/<과정>/tNN.json` (NN = 원본 문제 번호 두 자리). 문제 5개(a~e), `kind`는 원본 형식과 같게(빈칸 → blank, 한 줄 수정 → fix, 함수 작성 → write).
- **똑같으면 안 된다(저작권·변별)**: 원본 문장을 베끼지 않는다. 이야기(상황)·변수 의미·수치·예시를 새로 만든다. 5개끼리도 상황이 서로 달라야 한다.
- **형식·난이도는 비슷하게**: 원본이 연습시키는 핵심 기술(예: 2차원 리스트 행 순회 + 홀짝 판별, 한 줄 버그 종류, 함수 나누기 구조)을 그대로 연습하게 한다. 코드 길이·빈칸 수·함수 개수·제약 조건의 규모를 원본과 비슷하게. a는 원본보다 살짝 쉽게, b~d는 원본 수준, e는 원본 수준이거나 살짝 어렵게.
  - blank: 빈칸은 원본처럼 조건식·누적식·반환값·함수 호출 같은 핵심 자리에. 빈칸 수는 원본과 비슷하게(2~8).
  - fix: 원본 버그와 **같은 종류**의 버그(예: 반복 멈춤 조건, 초깃값, 누적식, 연산자, 반환문, 조건문)를 다른 코드에 넣는다. 틀린 코드는 예시에서 틀린 답을 내야 한다(무한 반복·오류로 멈추는 버그는 피한다). 고칠 줄이 하나뿐이어야 한다(다른 한 줄 수정으로도 맞게 되는 경우가 생기지 않게 주의).
  - write: 함수 머리와 `answer = 초깃값` / `return answer` 정도의 틀만 준다.
- 함수 이름은 COS Pro처럼 `solution`(보조 함수가 있으면 `func_a` 같은 이름이나 뜻 있는 이름).
- 문제 문장은 COS Pro 시험지 말투(합니다체). 중간 점검 질문·해설은 친절한 해요체. 모두 한국어.
- 매개변수 설명에 범위·조건을 분명히 쓰고, `inputCheck`로 그대로 검사한다. 동점·같은 값 처리 규칙이 필요하면 문제에 쓴다.
- 숨은 테스트 10~15개: 경계값(최소 길이, 최댓값, 동점, 음수/0 허용 시 그 값 등)을 꼭 넣는다. 테스트의 기댓값은 **정답 코드를 실제로 실행해** 만든다(손으로 쓰지 않는다).
- 중간 점검 3~5단계 권장 흐름:
  1. 문제 이해(mcq): 조건·규칙을 정확히 읽었는지(예: '이상' vs '초과', 몇 번째가 홀수 번째인지, 동점 처리).
  2. 손으로 따라가기(table): 예시 1(또는 작은 입력)을 반복마다 변수 값을 채운다. fix 문제는 **틀린 코드**로 따라가 보고 어디서 답이 어긋나는지 보게 하면 좋다. write 문제는 계산 과정을 표로.
  3. 핵심 결정(mcq 또는 short): 빈칸의 역할/틀린 줄 찾기/알맞은 접근 고르기. 코드 정답을 통째로 보기로 주는 것은 괜찮지만(시험처럼 고르기) 매 빈칸을 하나하나 다 알려 주지는 않는다.
  4. (선택) 경계 사례 확인(short/mcq).
  - 표의 정답은 `check`의 `answers()`가 계산한다. 가능하면 정답 함수 일부를 그대로 실행해 값을 만든다.
  - 학생은 사전 지식이 적다: 처음 나오는 용어(예: 인덱스, 슬라이싱, 누적)는 질문이나 해설에 짧게 풀어 준다.

1. 원본(문제지와 정답 포함본)을 읽고 핵심 기술·형식·난이도를 정리한다.
2. 스크래치 폴더(`/tmp/claude-0/-home-claude/f9ff8c2b-5b59-50ab-b880-76e35968603d/scratchpad/gen/<과정>-tNN/`)에 **Python 생성 스크립트**를 만들어 정답 함수로 기댓값을 계산하고 JSON을 쓴다(따옴표·줄바꿈 이스케이프 실수를 막는다). `ensure_ascii=False, indent=1`.

4. 스스로 점검: 문제 설명만 읽고 정답 코드를 쓸 수 있는가? 예시 설명이 값과 맞는가? mcq 정답이 정말 하나뿐인가? fix에서 다른 줄 하나를 고쳐도 통과하는 길이 있지는 않은가? blank에서 정답 외에 자연스러운 다른 답(예: `>=` 대신 `not <`)도 테스트를 통과하는가(통과해도 괜찮다 — 채점은 실행 결과로 한다)?
5. 다른 파일은 건드리지 않는다. git 명령(commit 등)은 하지 않는다.
